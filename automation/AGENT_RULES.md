# Rules for the agents (Planner, Generator, Healer, Reviewer, Backlog Scout)

Every agent in `.claude/agents/` reads this file first, and so does the coordinating session
of a night run (`automation/NIGHT_RUN.md`). Where it conflicts with an agent's own
instructions, this file wins. (The agent files are regenerated by
`npx playwright init-agents` after a Playwright update — keep project rules here, not there,
and re-add the one-line pointer to this file after regenerating.)

## The site

- Ucha.se dev: https://t.ucha.dev (Playwright project `ucha-dev`). Server-rendered
  PHP/Twig/jQuery, Bulgarian only.
- Many click handlers bind late — after jQuery is ready, sometimes after an AJAX call. A
  click that lands too early silently does nothing. That is timing, not a wrong selector:
  in test code use `clickWhenReady` from `utils/clickWhenReady.ts`.
- The dev server struggles under load and sometimes throws a multi-step form back to its
  first step. Before deciding a selector is wrong, check which page/step you're actually on
  and whether an error banner is showing.
- If the site doesn't answer, or shows "Softaculous Webuzo | Default Website Page", the
  environment is down (VPN). Stop — don't plan, generate or heal anything.

## Shell commands

Commands run under a fixed allowlist in night runs; anything else is refused, not asked about.
- The working directory is already the repo — never `cd`.
- Look at files with Read / Grep / Glob; use Bash for `git`, `npx playwright test`, `npx tsc`,
  `npx tsx`, `node`, `curl`, `python3`, `date`. Scratch files go in `/tmp`.
- No `$(…)`, backticks or heredocs. Commit with plain flags:
  `git commit -m "<subject>" -m "<body>" -m "Night-Run: …"`.
- A refused command isn't a reason to stop — split it, simplify it or use the dedicated tool.
  Never try to get around a refusal of `git push`, branch/history commands or protected files.

## Hard limits

- Never push or open PRs. Agents never commit either — they leave changes in the working
  tree. Only the coordinating session commits, locally, one commit per backlog item, adding
  the files it changed by name (never `git add -A`).
- Run only the spec file or test you were asked about — never the whole suite (it takes
  ~25 minutes and makes real sandbox payments).
- Payments: only the FIBank sandbox card (`test-data/fibank-test-card.ts`) and the ePay demo
  account (`test-data/epay-test-credentials.ts`). On `/set-data.php` the only allowed
  `fail_reason` is `101` (expired card), and it must be set back to `0` afterwards — every
  other value makes payments fail on dev for everyone.
- The shared accounts in `test-data/credentials.ts` are for looking around only: no
  password/email changes, no purchases, no deactivation. Flows that change account state use
  their own account on a fixed address (`testAddress('<label>')`) — via
  `utils/registerAndLogin.ts` with `test` from `utils/fixtures.ts` (deactivated automatically
  after the test), or as a story that deactivates the account as its last step and removes
  leftovers before and after (`removeAccounts`, see `tests/auth/student-account.spec.ts`).
  Never leave an account behind and never add a test that creates one per run on a new address.
- Emails are read from Mandrill with a key that can also see **other people's emails**. Only
  ever use `utils/mandrill.ts` (`expectEmail(address, Emails.…)` before the action, then
  `.link()` / `.received()` / `.arrivesWithin()`), which searches for one exact test address. Never call the Mandrill API yourself, never search with a partial address or
  without an address, never read, print or copy `.env`, and never put an email that isn't to a
  `kautotester+…` address into a log, a report or a commit.
- Don't edit `.env`, `playwright.config.ts`, `.claude/`, `automation/night/`, this file,
  `OPERATING_PROCEDURE.md` or git history. Only the coordinating session ticks items off in
  `automation/BACKLOG.md`; only the Backlog Scout adds items to it (see below).
- `- [?]` lines in `BACKLOG.md` are proposals waiting for the user's OK — never work on them.

## Planner

- Start from `tests/seed.spec.ts` (logged in as the shared student) or
  `tests/seed-guest.spec.ts` (not logged in).
- Save plans in `specs/`, named after the feature (e.g. `specs/school-code.md`).
- For each scenario, note what it needs: a fresh account, a paid subscription, data only an
  admin can provide (e.g. a real school code). Don't invent data — list it as an open question.

## Generator

- Follow the suite's structure: page objects in `pages/`, specs in `tests/<area>/`. Read the
  relevant page objects first and use them for every step they already cover.
- A step no page object covers may use a raw locator in the test, marked
  `// TODO(page object)` — it gets moved into `pages/` during review.
- Selectors: follow "Choosing selectors" in
  `automation/autoTest-skill/skills/autoTest/SKILL.md`. In short: role / label → `data-qa`
  → stable `id` → other stable attributes → text (for non-interactive content). No layout
  classes, no DOM position, no `.first()` / `.nth()` without a comment saying why.
- Assert the real Bulgarian text exactly as the site shows it.
- No `waitForTimeout`, no `networkidle`.

## Healer

Classify the failure before changing anything (details: "Self-healing" in
`automation/OPERATING_PROCEDURE.md`):

| What you find | What to do |
|---|---|
| Right page, element renamed/moved | Fix the selector from the live DOM |
| Element appears later / click did nothing | Use `clickWhenReady`; don't change the selector |
| Locator matches 2+ elements | Narrow by role, text or container — not `.first()` |
| Flow worked, but a text/value differs | **Don't** change the expected value — that's what a real bug looks like. Note it in `automation/ATTENTION.md`, mark the test `test.fixme()` with a one-line comment, stop |
| Wrong page, error banner, environment down | Not a test problem — note it in `ATTENTION.md`, don't edit the test |

- Log every fix you make in `automation/HEALING_LOG.md` (template at the top of that file;
  leave **Commit** as "not committed").
- At most 2 attempts per test. A test that already has a `HEALING_LOG.md` entry gets no
  second automatic fix — escalate to `ATTENTION.md` instead.

## Backlog Scout

Adds new items to `automation/BACKLOG.md` — only adds; never edits, ticks, reorders or
deletes existing lines, and never re-proposes anything in the "Rejected proposals" list.

**Low-risk — may be added directly as `- [ ]`** (night runs pick these up) only if *all* hold:
- Ucha.se dev only, and it's a user-facing behaviour with a clear pass/fail;
- it uses a guest, the shared student read-only, or a fresh account whose changes stay inside
  that account;
- no payment, no `/set-data.php`, no admin-panel data, no email to anyone but our own
  `kautotester+…` alias, nothing other users can see (comments, posts, invitations);
- it rests on evidence: a URL checked with curl, a Planner plan scenario, an `ATTENTION.md`
  note, a done item's "not covered" remark, or a documentation section;
- it isn't a duplicate of an existing, done, proposed or rejected item.

**Everything else is a proposal — `- [?]` under `## Proposed — needs your OK`.** Night runs
never pick those; the user approves or rejects them in chat.

At most 5 direct items and 10 proposals per run.
